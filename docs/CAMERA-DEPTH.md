# Depth-камера (OV02B1B, модуль AAC «B313») — состояние и находки

Обновлено: 2026-10-19. Пайплайн: `ov02b1b → msm_csiphy1 → msm_csid1 → msm_vfe1_rdi0` → `/dev/video4`.

## Что уже сделано и подтверждено на железе

| Факт | Как проверено |
|---|---|
| Сенсор сидит на **I2C 0x3c**, а не 0x59 | DT-узел `camera@3c`; драйвер проходит `check_sensor_id` (ждёт `0x2b`) |
| `0x59` — это **EEPROM 24c02** модуля («B313», 256 Б) | узел `atmel,24c02`; `at24 1-0059: 256 byte 24c02 EEPROM, read-only`; читается через sysfs |
| Сенсор виден на шине **только при `gpio66=1`** | скан CCI1: при 0 видно только 0x28/0x51/0x59, при 1 добавляется 0x3c |
| `gpio67` (SEL) не влияет на I2C, но **влияет на CSI** | при SEL=1 статусы CSIPHY1 нулевые, при SEL=0 есть активность |
| Пайплайн стартует без ошибок | `STREAMON` возвращает 0, VFE1 получает прерывание |
| Запись регистров доходит до сенсора | readback из драйвера: `0xfd = 0x3` (страница переключилась) |
| `0xc2` читается как 0 сразу после записи 1 | похоже на триггерную (самоочищающуюся) команду stream-on |

## Что НЕ работает

Кадров нет: `v4l2-ctl --stream-mmap` висит до таймаута, `/dev/video4` не отдаёт буферы.
`/proc/interrupts`: `camss_msm_csid1` = 0 (ни одного прерывания), `camss_msm_vfe1` = +1 (только старт).

## Диагностика CSIPHY (безопасный способ)

Регистры CSIPHY напрямую через `/dev/mem` читать **нельзя**, когда блок обесточен — это даёт fault
на шине и ребут SoC (поймано 2026-10-19). Правильный путь — принт из драйвера:

- `csiphy_lanes_enable()` (camss-csiphy-3ph-1-0.c) + `schedule_delayed_work()` на 2 с
- дамп `base + 0x800 + 0xb0 + 4*i`, i = 0..10 (это `CSIPHY_3PH_CMN_CSI_COMMON_STATUSn`)

Сравнение статусов (2 с после старта стрима):

| Камера | lanes | mask | статусы |
|---|---|---|---|
| задняя (работает) | 4 | 0x8f | `[0]=0x10 [1]=0x1 [3]=0x22 [5]=0x40 [6]=0x4 [8]=0x88 [9]=0x40` |
| передняя (работает) | 2 | 0x83 | `[1]=0x1 [3]=0x20 [9]=0x40` |
| **depth** | 1 | 0x81 | `[0]=0x4 [10]=0x4` (при SEL=1 — всё нули) |

У обеих рабочих камер есть `[1]=0x1` и `[9]=0x40`; у depth их нет. Похоже, PHY не видит
MIPI-клок/данные от сенсора, то есть сенсор не начинает передачу.

## Гипотезы (по убыванию вероятности)

1. **Init-таблица mainline-драйвера неполна для этого модуля.** В драйвере 94 регистра init +
   14 регистров режима. Вендорская последовательность лежит в
   `com.qti.sensormodule.c3q_aac_ov02b1b.bin` (Chromatix Parameter Parser V2.0.0) — формат
   бинарный, простым поиском массив не извлекается, нужен парсер.
2. **Аналоговые рельсы сенсора не включены.** В нашем DT `depth_vddio`/`depth_avdd` — пустышки
   `regulator-fixed, always-on` (`regulator_summary`: 0 mV, 0 потребителей по факту). Реальный
   источник (WL2866D выход 3/4 либо PM8008 L3P) не подтверждён; PM8008 на этом экземпляре не ACK'ает.
   Симптом «I2C работает, MIPI нет» сюда укладывается идеально.
3. **Мультиплексор (gpio66/67)** — SEL влияет на PHY, но правильная комбинация не найдена;
   проверены SEL=0/1 и порядок SEL→OE.

## Как воспроизвести тест

```sh
FMT="Y10_1X10/1600x1200"
media-ctl -d /dev/media0 -l '"msm_csiphy1":1 -> "msm_csid1":0 [1]'
media-ctl -d /dev/media0 -l '"msm_csid1":1 -> "msm_vfe1_rdi0":0 [1]'
for p in '"ov02b1b 1-003c":0' '"msm_csiphy1":0' '"msm_csiphy1":1' \
         '"msm_csid1":0' '"msm_csid1":1' '"msm_vfe1_rdi0":0' '"msm_vfe1_rdi0":1'; do
  media-ctl -d /dev/media0 --set-v4l2 "$p [fmt:$FMT]"
done
v4l2-ctl -d /dev/video4 --set-fmt-video=width=1600,height=1200,pixelformat=Y10P \
  --stream-mmap=2 --stream-count=5 --stream-to=/tmp/depth.raw
```

Правильный fourcc — **`Y10P`** (packed), не `Y10`: `camss-video.c` сравнивает его с форматом
сабдева и при несовпадении отдаёт `-EPIPE` до вызова `s_stream`.

## Попытка разобрать Chromatix-бин (2026-10-19)

`/vendor/lib64/camera/com.qti.sensormodule.c3q_aac_ov02b1b.bin` (54312 Б,
заголовок «QTI Chromatix Header» + «Parameter Parser V2.0.0 (1910091319)»).

Что удалось выяснить:

- файл — дерево узлов; запись узла ≈ 72 байта, имя — ASCII-строка на
  фиксированном смещении внутри записи, рядом лежат `parent_id`,
  `data_offset`, `node_id`;
- наивный скан по сигнатуре «печатное имя + sane-поля» даёт **716 узлов**;
- найдены нужные имена: `powerSetting` ×4, `regSetting` ×10,
  `registerData` ×130, `slaveAddr` ×130, `Data` ×130, `delayUs` ×130,
  плюс `sensorName` = `c3q_aac_ov02b1b`.

Что **не** получилось: раскодировать кодировку значений. Ни 3-байтовые
тройки (`addr16+val8`), ни 8-байтовые пары (`u32 addr + u32 val`, оба
порядка байт) не дают осмысленного массива — вместо регистров идут нули
и ASCII. Нужна спецификация Parameter Parser либо рабочий парсер.

**Практический обход**: снять состояние регистров сенсора *под Android*
после того, как CAMX его инициализировал (root + CCI), и сравнить с тем,
что пишет наш драйвер. Это даёт готовый «эталонный» дамп без разбора
формата.

## Попытка снять инициализацию из Android через ptrace (2026-10-20)

`strace`/`ftrace`/`debugfs` в вендорском ядре нет, поэтому был написан свой
перехватчик (`ioctlspy`, PTRACE_SYSCALL на все потоки HAL): он логирует
`ioctl()` и дампит буфер аргумента плюс память по указателям внутри него.

Что получилось:
- перехват работает: 115 735 строк, 6.4 МБ, видны V4L2-иоктлы
  (`0xc01856c0`, `0xc0306201`, `0xc0180902`, ...);
- но полезная нагрузка — **структуры с указателями** в разделяемую память,
  а не сами регистры; офлайн-разбор 10 454 блоков не нашёл таблицы
  `(addr, val)` — только нули, код и указатели.

Вывод: без знания раскладки структур вендорского HAL регистры так не достать.
Побочный урок: перехватчик надо снимать через `PTRACE_DETACH`, иначе потоки HAL
остаются в остановленном состоянии (камера «фатальная ошибка» до перезагрузки).

## Вендорский дамп CSIPHY1 (2026-10-26) — найдена причина

В Android-ядре есть параметр `csiphy_dump`:
`/sys/module/cam_csiphy_core/parameters/csiphy_dump`. С `debug_mdl = 0xC020`
(`CAM_SENSOR|CCI|CSIPHY`) и `csiphy_dump = 1` при открытии depth-камеры (ID 2)
снимается полный дамп регистров CSIPHY.

### Что отдаёт сток для depth

| Регистр | Значение | Смысл |
|---|---|---|
| `0x814` LANE_ENABLE | **0x50** | lanes 2 и 3 (bits 4 и 6), бит `CLK_ENABLE` (0x80) **не выставлен** |
| блок `0x400` (lane2) | `0x8d, 0x0c, 0x14, 0x00, 0x02, 0x80, …` | **data**-паттерн |
| блок `0x600` (lane3) | `0x80, 0x0c, 0x14, 0xa5, 0x02, 0x80, 0x0e, 0x1f, 0xb8` | **clock**-паттерн |
| блок `0x700` (clock) | **0** | не используется |
| блоки `0x000`, `0x200` | **0** | не используются |
| settle `0x408` / `0x608` | **0x14 = 20** | у mainline расчёт даёт 3 |

Для сравнения задняя камера (4 линии): `0x814 = 0xd5`, блок `0x700` = clock,
блоки `0x000..0x600` = data, settle `0x12 = 18`.

### Как это устроено в стоке

`cam_csiphy_config_dev()` (camera-bengal) считает `lane_enable` из маски,
которую присылает HAL:

```
lane_mask 0x18 (depth)  → lane_enable = BIT(4) | BIT(6) = 0x50
lane_mask 0x1f (rear)   → lane_enable = 0xd5 (BIT0|BIT2|BIT4|BIT6|BIT7)
```

где `BIT(2*p)` — линия `p`, а `BIT(7)` — отдельный clock-блок. Depth приходит
с `lane_cnt = 1`, `combo_mode = 1`: сток гоняет его как **DPHY combo mode**, и в
combo-таблице строка для lane3 (`0x600`) содержит clock-значения.

Вывод: **CSI-мультиплексор заводит depth на lane2 (data) + lane3 (clock)**, а
mainline всегда программирует lane0 + clock-блок `0x700`. Сенсор при этом
исправно принимает I2C, но его MIPI физически приходит на другие линии —
отсюда `status[0..10] = 0`.

### Что сделано в mainline

- `sm6225-xiaomi-fog.dts`: у `ov02b1b_ep` и `csiphy1_ep` теперь
  `clock-lanes = <3>; data-lanes = <2>;` (было `<7>` / `<0>`).
- `camss-csiphy-3ph-1-0.c`: добавлена таблица `lane_regs_sm6225_clk3[]`
  (вендорские clock-значения для блока `0x600`) и запись таблицы вынесена в
  `csiphy_write_lane_regs()`. Если `clk.pos == 3`, блок lane3 перепрограммируется
  как clock-линия.
- `csiphy_lanes_enable()`: при `clk.pos == 3` CTRL5 = `BIT(6) | BIT(data*2)`
  вместо `CLK_ENABLE | BIT(data*2)`, то есть `0x50` — как у стока.

Проверка на железе — через автотест `camtest.sh` в rescue-initramfs: он сам
поднимает пайплайн, стримит, снимает статусы CSIPHY и dmesg, пишет отчёт в
`/cust/camtest.log` и перезагружается в Ubuntu (откуда лог забирается по adb).

## Итерация 2026-10-26 (вечер): PHY приведён к вендору, кадров всё ещё нет

### Сделано и проверено на железе

1. **Линии CSIPHY приведены к стоковой раскладке.** В DT: `clock-lanes = <3>; data-lanes = <2>;`
   (было `<7>`/`<0>`). В драйвере — таблица `lane_regs_sm6225_clk3[]` и CTRL5 без бита
   `CLK_ENABLE` при clock на lane 3. Проверено чтением регистров во время стрима:

   | Регистр | Наше значение | Вендор (dump) |
   |---|---|---|
   | `0x814` LANE_ENABLE | `0x50` | `0x50` |
   | `0x400` (lane2 cfg0) | `0x8d` | `0x8d` |
   | `0x600` (lane3 cfg0) | `0x80` | `0x80` |
   | `0x60c` | `0xa5` | `0xa5` |
   | `0x638` | `0x1f` | `0x1f` |
   | `0x408` / `0x608` settle | `0x14` | `0x14` |
   | `0x0B00/0x0B04/0x0B08` | `5 / 7 / 0x10` | `5 / 7 / 0x10` |
   | `0x0C00/0x0C04/0x0C08` | `5 / 7 / 0x10` | `5 / 7 / 0x10` |

   То есть PHY теперь запрограммирован **байт-в-байт как в стоке**.

2. **settle = 20** (вендорское значение) для этого случая вместо расчётных 3.

3. **Init-таблица заменена на полную (92 записи).** Важное открытие: `cam_cci` в логе печатает
   только **первую пару** каждой burst-записи (`cmd_size` убывает на несколько байт), поэтому
   извлечённая ранее «вендорская таблица» на 70 записей была неполной. Полная таблица взята из
   рабочего mainline-порта (`map220v/sm8550-mainline`, 92 записи) — она содержит те регистры,
   которых не было: `0x19/0x1b/0x20/0x30/0x31/0x38/0x4e/0x4f/0x50/0x35/0x45…0x48/0x56…0x5b/
   0x37/0x42/0x68…0x6a/0x7c…0x7f/0x83/0x84/0x86…0x88/0x94/0x98` и блок страницы 3.

4. **Проверено, что записи драйвера реально доходят** (раньше сбивал с толку debug-дамп
   драйвера — он читал не ту страницу): прямыми `i2cget` подтверждено
   `p1 0x0e=0x06, 0x0f=0x0b, 0x22=0x38`, `p3 0x97…0xac`, `p0 0x5a=0x15, 0x74=0x01`,
   `p3 0xc2=0x01`.

### Что исключено экспериментально

| Гипотеза | Результат |
|---|---|
| Питание AVDD (WL2866D) | `0x0e=0x0f`, `0x05/0x06=0x80` (2.8 В по вендорскому драйверу) — норма |
| MCLK | `gcc_camss_mclk1_clk` 19.2 МГц, `pin 21 = cam_mclk`, владелец `1-003c` |
| CSI-мукс `gpio67` | в стоке пин вообще не используется (в DT только `gpio21/65/66`); проверены оба уровня — без разницы |
| `settle_cnt` 3 → 20 | без изменений |
| Маршрут `csiphy1 → csid1 → vfe1` | без кадров |
| Маршрут `csiphy1 → csid2 → vfe2` (как в стоке: активен `tfe2`) | без кадров |
| `lane_assign` CSID 2 → 0 | без изменений |
| Refresh-блок вендора после `c2=1` | без изменений |
| Блок `0x700` (лишний clock-маркер) | обнуление на ходу — без изменений |
| `0xfb` страницы 3 | регистр только для чтения, всегда 0 |

### Текущее состояние

`VIDIOC_STREAMON` проходит, `lane_enable=0x50`, все регистры сенсора и PHY совпадают с
вендорскими, `p3 0xc2=1` (сенсор в стриме), но:
- `/proc/interrupts`: `camss_msm_csiphy1` = **0** (IRQ размаскированы — активность на линиях
  отсутствует),
- `camss_msm_csid1`/`vfe1` — только стартовые прерывания,
- буферы не завершаются, кадров нет.

Вывод: сенсор не выводит MIPI-поток, хотя по регистрам он «в стриме». Осталось выяснить, чего
не хватает сенсору — вероятнее всего, отличия в burst-записях вендорской init-таблицы
(лог их не показывает) либо ещё один шаг, который HAL делает после `c2=1`.

### Инфраструктура для следующей итерации

- `camtest.sh` в rescue-initramfs: сам поднимает пайплайн, стримит, снимает статусы CSIPHY и
  dmesg, пишет отчёт в `/tmp/camtest.log` (+ `/cust/camtest.log`) и дублирует на ACM-консоль.
  Маркер-файл `/camtest-route2` переключает тест на маршрут `csiphy1 → csid2 → vfe2`.
- `gpio67` выведен как LED `/sys/class/leds/csi-mux-sel` — можно переключать без пересборки.
- Внимание: `v4l2-ctl --stream-mmap` без кадров уходит в D-state и не убивается; при
  `hung_task_panic=1` это через ~120 с роняет ядро. Для интерактивных тестов запускать только
  в фоне и не оставлять висеть.

## Инструментация CSID и комбо-режим (2026-10-26, поздняя итерация)

### Что показывает CSID во время стрима

Добавлены чтения регистров CSID в автотест (`camtest.sh`). Во время стрима:

| Регистр | Значение | Расшифровка |
|---|---|---|
| `0x070` IRQ_STATUS | `0x0` | событий нет |
| `0x074` IRQ_MASK | `0x1` | размаскирован только `RST_DONE` |
| `0x100` CSI2_RX_CFG0 | `0x00200020` | 1 линия, lane_assign=2, phy_sel=2 (csiphy1), DPHY |
| `0x300` RDI0 CFG0 | `0x802BF000` | **enable=1**, decode_format=0xB, **DT=0x2B (RAW10)**, VC=0 |
| `0x308` RDI0 CTRL | `0x1` | resume at frame boundary |

То есть CSID настроен верно и включён, но **пакетов не получает**.

Попытка размаскировать все прерывания CSID (`0x074 = 0xffffffff`) не удалась: регистр
принимает только бит `RST_DONE` (читается обратно `0x1`), поэтому ошибки CSID
аппаратно не наблюдаемы. В ISR теперь логируется значение статуса вместо
бесполезного «Spurious CSID interrupt».

### Вендорский DT: на CSIPHY1 два слота сенсоров

`khaje-camera-sensor-idp.dtsi`:

| cell-index | csiphy-sd-index | что |
|---|---|---|
| 0 | 0 | задняя (S5KJN1) |
| 1 | 2 | фронтальная (hi556) |
| **2** | **1** | **depth (OV02B1B)** |
| **3** | **1** | альтернативный сенсор на том же разъёме (MCLK3 = gpio28, reset = gpio19) |

Это и есть смысл combo mode: один PHY обслуживает два посадочных места, каждое
со своей парой линий. На нашем экземпляре распаян только depth (cell-index 2,
MCLK1/gpio21, reset gpio65).

### Тайминги и значения старта из свежего CCI-лога

- блок старта вендора: `0x22=0x1f` (gain), `0x0e/0x0f = 0x04d6` (**экспозиция 1238 =
  длина кадра**), `0x14=0x00`, `0x9b=0x40`, `0xfe=0x02`;
- между этим блоком и `c2=1` — пауза **70.8 мс**.

Раньше у нас экспозиция была 1547 (> длины кадра 1238), что для OV-сенсора
невалидно. Обе вещи исправлены в драйвере.

### Состояние

Регистры PHY совпадают с вендорскими (включая combo-бит `0x428=0x0a`), CSID
сконфигурирован и включён, сенсор в стриме — но ни CSID, ни VFE не видят пакетов.
